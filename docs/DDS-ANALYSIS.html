1. Сжатый контекст (можно копировать в LLM целиком)

Проект: одностраничный дашборд «Движение денежных средств» (ДДС, прямой метод) на русском языке.
Стек: React 19.2 + TypeScript 5.9 + Vite 7.3 + Tailwind 4.1 (плагин @tailwindcss/vite), сборка в один HTML (vite-plugin-singlefile).
Бэкенда нет. Данные синтетические, генерируются при импорте модуля src/lib/data.ts (детерминированный PRNG, без сети и файлов).
Объём: ~2 285 строк TS/TSX в src, 130 строк тестов, 28 файлов в git.
Точка входа: src/main.tsx → src/App.tsx.
Слои:
  • данные/домен:  src/lib/data.ts (дерево статей, префиксные суммы по дням, сценарии, контрагенты)
  • календарь:     src/lib/dates.ts (дни 0..1095 = 2024-01-01..2026-12-31, недели/месяцы/кварталы, границы сценариев)
  • колонки:       src/lib/columns.ts (дерево периодов → header cells с rowspan/colspan)
  • вычисление:    src/lib/model.ts (buildModel: строки × колонки → матрица значений, теплокарта)
  • настройки:     src/lib/settings.ts (Settings, localStorage, пресеты, сохранённые виды)
  • действия:      src/lib/rowActions.ts (свернуть/скрыть/solo/восстановить)
  • формат/экспорт: src/lib/format.ts, src/lib/exportCsv.ts
  • UI:            src/App.tsx, components/{ScenarioTabs,Toolbar,Kpis,PivotTable,Drilldown,SidePanel,ui}.tsx
Ядро модели: у каждой статьи есть Float64Array prefix длиной 1097 (префиксные суммы по дням).
Значение статьи за [s,e] = prefix[e+1] − prefix[s]; «нарастающим» — от начала периода; «% выручки» — деление на поступления группы op_in.
Сценарии: fact (базовые данные), plan/budget (fact × случайный множитель по дням), rolling (склейка fact→plan→budget по границам), compare и planfact (4 метрики на период).
Границы: дата отреза факта нормализуется к воскресенью, конец оперплана — к концу месяца.
Ряды: 45 статей = 29 листьев + 13 групп + 3 расчётных (остаток на начало, чистый поток, остаток на конец); знак расходов отрицательный.
Настройки и «виды» хранятся в localStorage (ключи dds-pivot-settings-v2 / dds-pivot-views-v2).
Качество: npm test = 14/14 pass, npm run build = OK (609 кБ, 319 кБ gzip), но npx tsc --noEmit = 5 ошибок; CI, линтера, README и скрипта typecheck нет.

4. Технологии и окружение

  • React 19.2.6, react-dom 19.2.6, useState/useMemo/useCallback — без внешнего state-менеджера и без роутера.
  • TypeScript 5.9.3, strict: true, noUnusedLocals, noUnusedParameters, noFallthroughCasesInSwitch, noEmit, alias @/* → src/* (на практике импорты относительные).
  • Vite 7.3.2 + @vitejs/plugin-react 5.1.1 + vite-plugin-singlefile (весь JS/CSS/шрифты инлайнятся в один HTML — 7 встроенных woff2).
  • Tailwind CSS 4.1.17 через @tailwindcss/vite; дизайн-токены — CSS-переменные в src/index.css, кастомный вариант dark.
  • lucide-react 1.70.0 (иконки), clsx + tailwind-merge (утилита cn).
  • @fontsource-variable/inter — шрифт в бандле, а не с CDN.
  • Тесты: самодельный раннер — esbuild собирает tests/*.ts(x) в .test-build/*.cjs, затем node --test. DOM-окружения нет: UI проверяется через react-dom/server.renderToStaticMarkup, интерактив не тестируется.

6. Поток данных и вычислений

localStorage ──loadSettings──┐
                            ├─→ useState<Settings> st ──┐
query (поиск) ──────────────┘                          │
                                                       ▼
                          buildModel(st, query) ──────────────→ Model
                            ├─ clampRange(st)                    { rows, cols, header,
                            ├─ rollingBounds(factCutoff, planEnd)  headerRows, values,
                            ├─ buildTree(levels, s, e)             rangeS, rangeE, heatMax }
                            ├─ layoutColumns(...)
                            ├─ buildRows(st, query)
                            └─ values[i][j] = cellValue(row, col, st, s, bounds)
                                        │
                     articleValue(article, s, e, rangeStart, mode, scenario, bounds)
                                        ▼
                     scenarioPrefix(article, scenario, bounds) → Float64Array(1097)
                                                       │
        PivotTable ◄── Model ──► Kpis (scenarioTotals)
             │                      ▲
             ├─ Drilldown (cellValue + counterpartyValues)
             └─ exportCsv ──────────┘

Ключевые формулы

  • prefix[i+1] = prefix[i] + daily[i], i = 0..1095 (день 0 = 2024-01-01, UTC).
  • Значение за период: value(s..e) = prefix[e+1] − prefix[s].
  • «Нарастающим итогом»: from = rangeStart, иначе from = s; pct = value / revenue(op_in).
  • Остаток на начало: OPENING_BALANCE + net[s]; на конец: OPENING_BALANCE + net[e+1]; OPENING_BALANCE = 35 000 000.
  • Ролинг-форкаст: дневное значение берётся из fact при i ≤ factEnd, из plan при i ≤ planEnd, иначе из budget.
  • План/бюджет: daily = round(fact_daily × k / 100) × 100, где k ∈ [1.04, 1.16] для плана и [0.88, 0.98] для бюджета, PRNG с seed от id статьи.
  • Δ и % в compare/planfact: delta = value(scenario) − value(budget); % вып. = |actual| / |plan| × 100; % откл. = (|actual| − |plan|) / |plan| × 100 (по модулям, поэтому знак отклонения читается как «больше/меньше плана по величине»).

Инварианты, которые обязаны сохраняться при доработках

  1. Аддитивность по времени: сумма значений по непересекающимся соседним периодам равна значению за объединение (проверено для rolling и для колонки «Итого»: 59 204 600 = сумме 12 месяцев).
  2. Согласование итогов: сумма листьев = NET = scenarioTotals.net; close = open следующего дня (тесты 10).
  3. Клиппинг факта: в матрице факт после factEnd даёт null, но scenarioTotals факт не клиппит.
  4. Скрытие не меняет итог группы: строка «Скрытые статьи» дорисовывается как group − сумма(видимые листья).
  5. Сетка колонок покрывает период без пересечений, недели режутся границами уровней.
  6. Кэш сценариев зависит от (scenario, article, factEnd, planEnd) — при смене границ ключ меняется.

7.1 Дерево статей (45 статей)

   ├─ Маркетинг (mkt)                       Контекст, Таргет, Агентства

Генераторы: daily (база × сезонность × рост × шум, пропуски и коэффициенты выходных), monthly (фиксированные дни месяца), sporadic (вероятность), dates (жёстко заданные даты: кредиты, дивиденды). Расходы хранятся со знаком минус.

7.2 Сценарии и границы

Сценарий Что показывает Как строится период вкладки
fact фактические данные с 2026-01-01 до воскресенья даты отреза
budget бюджет с конца оперплана + 1 до 2026-12-31
plan оперплан с дня после отсечки до конца месяца оперплана
rolling склейка факт→план→бюджет весь 2026 год
compare бюджет vs ролинг, Δ и % вып. весь 2026 год, уровни принудительно month
planfact план (бюджет), факт, отклонение, % отклонения весь 2026 год, уровни принудительно month

Границы: normalizeFactCutoff сдвигает дату к ближайшему воскресенью, normalizePlanEnd — к концу месяца. По умолчанию: отсечка 2026-03-15, конец оперплана 2026-04-30, бюджет с 2026-05-01.

7.3 Колонки

buildTree(levels, s, e) строит вложенное дерево: каждый уровень режется segments() внутри родителя. Ключ колонки — level:start-end, у сценарных колонок добавляется префикс scenario: и суффикс в заголовке. layoutColumns разворачивает дерево в «ячейки шапки» с colspan/rowspan, добавляет подытог (Σ) слева/справа от детей и закреплённую справа колонку «Итого». Ручные переопределения хранятся в st.colOverrides[key] = collapsed?.

compare/planfact — пост-обработка: каждая базовая колонка размножается на 4 метрики (48 колонок за 12 месяцев, 52 с «Итого»), шапка становится двухуровневой (headerRows = 2).

7.4 Строки

buildRows обходит ROOTS: учитывает hiddenRows (скрытие не влияет на итоги), collapsedRows, добавляет виртуальную строку id::rest «Скрытые статьи (n)», при поиске игнорирует скрытие и раскрывает предков найденного. Действия возвращают патч настроек, а не мутируют состояние — это аккуратная и полезная архитектурная деталь.

7.5 Значения и формат

makeFormatter считает нулём всё, что меньше 0.5 × 10^-d в единицах отображения, рисует –, поддерживает скобки и U+2212. Знак расхода отрицательный, поэтому «Выплаты» в KPI отрицательные, а Δ для выплат считается от −out.

7.6 Настройки и виды

Settings — один плоский объект (~30 полей), сохраняется целиком в localStorage на каждое изменение. VIEW_KEYS — подмножество полей, попадающих в «вид» (без темы и закрепления панели). PRESETS — 5 готовых видов (собственник, финконтроль, недели, дни, структура затрат в %).

9. Критический разбор

9.0 Вердикт

Это крепкий интерактивный прототип с продуманным UI и аккуратной вычислительной базой (префиксные суммы, чистые патчи, детерминированные данные), но не продукт:

  • данные синтетические, а «план» и «бюджет» выводятся из факта — то есть вся аналитика план-факт и сравнение измеряют шум генератора, а не планы;
  • проверки качества декоративны: типы не проверяются, CI нет, тесты не ловят ни одного из найденных ниже дефектов;
  • часть чисел на экране может противоречить другим числам на том же экране (KPI vs таблица), а периоды — молча переворачиваться;
  • интерфейс выглядит убедительнее, чем модель: «контрагенты», «% выполнения», «Δ» создают впечатление аналитики, которой в данных нет.

Ниже — по приоритетам, с воспроизведением.

P0-1. Демо-данные вместо данных

data.ts при импорте генерирует 29 листьев на 3 года и собирает префиксные суммы. Ни API, ни загрузки файла, ни парсинга CSV, ни слоя адаптеров. «Настраиваемый дашборд» без источника данных — это демо-витрина; всё остальное (сценарии, контрагенты, границы) существует только для этой синтетики.

Что это значит для доработок: прежде чем добавлять фичи, нужен контракт данных (interface CashflowDataset), стор и загрузчик; иначе любая новая функция будет прибита к генератору.

P0-2. Циркулярная аналитика плана
// src/lib/data.ts:274-278
const base = a.prefix[i + 1] - a.prefix[i];
const factor = scenario === "plan" ? 1.04 + random() * 0.12 : 0.88 + random() * 0.10;
daily[i] = Math.round(base * factor / 100) * 100;

План и бюджет считаются от факта по дням. Последствия:

  • «Отклонение факт − план» — это не отклонение от плана, а факт × (1 − k), где k — случайный множитель; план никогда не бывает «независимым».
  • Невозможно смоделировать нормальную ситуацию «план рос, факт упал»: бюджет копирует все всплески и провалы факта.
  • Метрики % вып. (в compare) и % отклонения (в planfact) наследуют эту зависимость, поэтому «инсайты» на демо недостоверны по построению.
  • Тест planfact analysis works on past periods (2024) закрепляет именно это поведение как норму — то есть тест охраняет не бизнес-правило, а артефакт генератора.

Как чинить: генерировать план независимо (свой сезонный профиль и шаг роста) и хранить его отдельным набором префиксов; факт получать как «план + независимый шум + сдвиги». Тогда отклонения станут осмысленными.

FACT_END_DAY используется в model.ts:181, но не импортирован из dates.ts (строка 4 импортирует LEVEL_ORDER, isoToDay, TOTAL_DAYS, rollingBounds, SCENARIO_LABELS, Scenario). В приложении это не падает только потому, что buildModel всегда передаёт bounds; любой вызов cellValue без bounds даёт ReferenceError — проверено:

Причина, почему это дожило до ветки: npm run build — это vite build (esbuild стирает типы), а test собирает esbuild'ом. Ни одна команда проекта не проверяет типы. Коммит при этом утверждает «Тесты 14/14, build OK» как доказательство качества.

P0-4. KPI и таблица считают разное

Kpis берёт scenarioTotals(...), а таблица — cellValue, где факт обрезается по factEnd. scenarioTotals обрезку не делает (scenario === "fact" → a.prefix без клиппинга). В режиме «Факт» стоит расширить период за 15.03.2026 — и на одном экране:

таблица (сумма колонок «Факт»): −15 392 800
KPI «Чистый денежный поток»:    −7 372 300

Плюс заголовок App.tsx:156 для вкладки «Факт» вообще не сообщает, что факт обрезан. Для финансового дашборда расхождение двух чисел на одном экране — это дискредитация всего продукта, независимо от того, какое из них «правильное».

Как чинить: один источник истины для «доступного факта» (функция effectiveRange(scenario, s, e)), использовать её и в cellValue, и в scenarioTotals, и в KPI, и в экспорте; плюс явная плашка «факт доступен до …».

P0-5. Перевёрнутые периоды

scenarioPeriods жёстко зашивает 2026-01-01 и 2026-12-31:

fact:   { from: "2026-01-01", to: dayToIso(factEnd), ... },
budget: { from: dayToIso(budgetStart), to: "2026-12-31", ... },

Проверка на реальном коде:

scenarioPeriods("2024-06-01", "2026-04-30")
  fact:   { from: "2026-01-01", to: "2024-06-02" }   ← начало позже конца
  plan:   { from: "2024-06-03", to: "2026-04-30" }   ← 2 года «оперплана»
scenarioPeriods("2026-11-20", "2026-04-30")
  plan:   { from: "2026-11-23", to: "2026-04-30" }   ← перевёрнуто

clampRange в model.ts:86 молча меняет s и e местами (if (e < s) [s, e] = [e, s]), поэтому пользователь получит таблицу за диапазон, который не выбирал, без единого предупреждения. То же при выборе даты отсечки после конца оперплана — а это штатное действие в UI.

Как чинить: валидировать ввод (запрещать planEnd < factCutoff, factCutoff вне поддерживаемого окна), вычислять from от выбранной отсечки, а не от константы, и показывать явную ошибку вместо тихого свапа.

P1-1 подробнее. % вып. = |факт| / |план| × 100; защита есть только от точного нуля. На реальных данных это будет постоянно; нужен порог (|plan| < ε → «н/д») и/или абсолютное отклонение рядом с относительным.

P1-2 подробнее. counterpartyValues делит сумму статьи между пятью вымышленными контрагентами по хешу от id, причём mode жёстко 'sum' и не передаётся col.node.delta. Поэтому в «Нарастающим» и в колонках «Δ» разбивка не сходится с итогом расшифровки, а в «Факте» после отсечки показывает числа под пустой ячейкой. Для демо это допустимо, но подпись «По контрагентам» обещает аналитику, которой нет; в проде это надо либо убрать, либо питать реальными разрезами.

9.3 P2 — гигиена, поддерживаемость, риски

  • Мёртвый код и легаси: Settings.comparison не читается нигде, кроме определения; SCENARIO_PERIODS помечен «Legacy defaults»; IN_PREFIX/OUT_PREFIX считаются при импорте, но за пределами data.ts не используются (лишние ~35 кБ и работа); delta?: "plan" | "budget", хотя используется только budget; LEVEL_ORDER[n.level] с приведением типа для "total".
  • Магические числа: OPENING_BALANCE = 35 000 000, TOTAL_DAYS = 1096, окно 2024–2026, порог 0.5, коэффициент теплокарты 0.34, коэффициенты генератора — всё в коде, без конфигурации.
  • Дубли и хрупкость: список «расходных» id захардкожен дважды в PivotTable.tsx:169,174; для смешанных групп (inv, fin) эвристика «всё расход» неверна по смыслу; знак и цвет выводятся из этого списка, а не из данных.
  • Кэш сценариев не ограничен: ключ включает factEnd/planEnd, и каждая новая комбинация при переборе дат добавляет ~43 массива × 8.8 кБ ≈ 380 кБ. При аккуратном перетаскивании границ это накопится; TTL/LRU нет.
  • Репозиторий: нет README, LICENSE, CONTRIBUTING, .editorconfig, линтера/форматтера, CI-workflow; package.json называется react-vite-tailwind, версия 0.0.0; в git лежит собранный dist/index.html на 600 кБ (он актуален, но раздувает диффы).
  • История git: main (39b3554) и ветка (36b6fc0) — несвязанные истории (git merge-base отсутствует), т.е. PR/мерж потребует --allow-unrelated-histories; единственный «фиксящий» коммит добавляет все 28 файлов и 5 223 строки, поэтому по истории невозможно понять, что именно чинилось.
  • Тесты: 14 штук; UI проверяется сравнением HTML-строк (renderToStaticMarkup), интерактив (клик, сворачивание, экспорт, localStorage) не покрыт; нет e2e, a11y, перф-тестов, покрытия и порогов. Тест assert.equal(m.cols.length, 48) закрепляет реализацию, а не требование.
  • Локализация: только русский, Intl жёстко ru-RU, подписи в JSX, нет слоя i18n; расчёт в UTC (для Москвы безобидно, для мультирегиона — нет).
  • Отсутствие устойчивости: нет error boundary, скелетонов/состояний загрузки (данные синхронны), обработки пустого результата на уровне приложения, телеметрии и логирования.
  • Сохранение настроек: синхронная запись в localStorage на каждое изменение (включая перетаскивание слайдера ширины).

9.4 Что я проверил и проблемой не считаю

Чтобы критика была честной, эти вещи я специально проверял — они в порядке:

  • Сборка в один файл воспроизводима, закоммиченный dist совпадает с текущим билдом.

3. Критическая оценка скиллов (а не только списка)

  1. Скилл — это промпт-каркас, не анализатор. Ни один из них не парсит AST и не доказывает утверждения; ценность — в дисциплине (фазы, обязательные ссылки file:line, чек-листы). Всё содержательное всё равно добывается чтением кода и запуском тестов.
  2. Звёзды ≠ качество. project-rebirth-skill (0★) концептуально ближе к задаче, чем ctf-skills (3.6k★); у codebase-analysis-skill всего 41★, но есть методика и скрипты верификации. Звёзды у obra/superpowers (314k) и anthropics/skills (190k) — популярность, а не пригодность к RE.
  3. Лицензии разные: у anthropics/skills и Repo-Analyzer-Skills файла лицензии нет — для внутреннего использования уточняйте у правообладателя; markdown-viewer/skills — CC-BY-4.0 (нужна атрибуция).
  4. Расхождение в README у codebase-analysis-skill: инструкция по установке ссылается на github.com/Yangchengshuai/... (старое имя/форк), а репозиторий живёт под Ycsyyds. Перед установкой проверяйте, что клонируете именно то, что читали.
  5. Риск «уверенной чуши». Скиллы генерят красивые документы; без требования [VERIFY: file:line] и без прогона кода в них появляются несуществующие функции и «архитектурные решения», которых не было. В моём документе каждая претензия сопровождается ссылкой и воспроизведением — это и есть разница между RE и пересказом.
  6. Установка = исполнение чужого кода. Большинство скиллов предлагают клонирование в ~/.claude/skills или плагин-маркетплейс; читайте SKILL.md, scripts/, helpers/ до запуска, особенно если скилл включает shell/python-шаги.
  7. Для 2,3 тыс. строк скилл — оверхед. Этот проект целиком читается за один проход (2 498 строк, включая тесты). Скилл дал бы шаблон отчёта и чек-лист полноты, но не новые факты.

5. Что я рекомендую не делать

  • Не запускать скиллы «для галочки» и не принимать их выводы без проверки кодом — в этом репозитории цена ошибки высокая: неверно описанный инвариант (например, «факт не обрезается») приведёт к regression в финансовых числах.
  • Не позволять скиллу переписывать код в рамках «анализа»: сначала документ и тесты, потом изменения.
  • Не тащить бинарные RE-паки (CTF/Ghidra/Frida) — они не про этот класс задач.
  • Не строить процесс на репозиториях с 0–4★ без собственного ревью SKILL.md; и наоборот, не игнорировать маленькие репозитории только из-за звёзд.
